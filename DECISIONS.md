# Decisions

Record of choices made where the spec left a detail unspecified. Each entry: what was unspecified, the choice made, and why it's the simplest option consistent with the spec.

## Scaffolding

- **Package manager / monorepo tool**: npm workspaces, as explicitly required by the spec ("Monorepo with npm workspaces. Package manager: npm."). No Turborepo/Nx layer added — not needed for 3 workspaces and the spec says not to add anything beyond what's listed.
- **TypeScript strictness**: root `tsconfig.json` uses `"strict": true` and `"noUncheckedIndexedAccess": true`. Not specified, but it's the simplest config that catches RLS/role-handling bugs at compile time, which matters given the spec's emphasis on server-side enforcement.
- **Module resolution**: `"moduleResolution": "Bundler"` at the root since both Next.js 15 and Expo's Metro bundler expect bundler-style resolution; each workspace's own tsconfig extends this and can override if a tool requires otherwise (e.g. Expo's own base config).
- **Shared package import path**: `@roughcut/shared` as the workspace package name/import alias, since the spec just says "shared types in /packages/shared" without naming a package name.
- **seed script runtime**: `node --experimental-strip-types supabase/seed/seed.ts` (Node 20+ can run a `.ts` file directly with this flag) rather than adding `ts-node` or `tsx` as a dependency — simplest option with no extra dev dependency. If this doesn't work in the Node version available at deploy time, revisit by adding `tsx` as a devDependency.

## Schema, RLS, seed

- **subscription_status column type**: `text`, not an enum. The spec requires mapping raw Stripe webhook statuses (`active`, `trialing`, `past_due`, `canceled`, `unpaid`, `incomplete`, `incomplete_expired`) plus a `free` value with no Stripe subscription at all. Stripe can add statuses; a free-form column avoids a migration every time.
- **public_code generation**: 12 random characters from a 32-character unambiguous alphabet (lowercase letters + digits, excluding `0/o/1/i/l`), generated server-side in a `before insert` trigger with a uniqueness retry loop. Meets "unguessable, not sequential" without pulling in an external ID library.
- **short_code generation**: `RC-####` computed as `(count of existing boxes for the company) + 1`, zero-padded to 4 digits, also in the `before insert` trigger. Spec only requires "unique per company," not unguessable, so a simple counter is the simplest option.
- **Column-level permission enforcement (installer vs. foreman/admin on `boxes`)**: RLS policies are row-level only, so a `before update` trigger (`enforce_box_update_rules`) additionally enforces that installers may only flip `status` to `installed` (and only touch `installed_by`/`installed_at` while doing so), and that `status = 'installed'` can never revert for anyone. This is enforcement, not UI hiding, per the spec's explicit requirement.
- **Plan caps enforcement location**: enforced in a DB trigger (`enforce_job_caps`, `enforce_box_caps`, `enforce_invite_caps`) as defense-in-depth, *and* intended to be checked again in the Next.js server actions before insert so the user gets a friendly 402 response rather than a raw Postgres error. The trigger raises with `errcode = 'P0402'` so the web layer can detect it specifically.
- **Audit log writes**: no RLS insert policy for authenticated roles at all — only the service role (server actions/admin routes) can write `audit_log` rows, which matches "Log admin actions to an audit_log table" being a server-side responsibility.
- **Box photo storage path RLS**: storage policies key off the first path segment of the object name, which the spec already fixes as `{company_id}/{box_id}.jpg`, so `storage.foldername(name)[1] = company_id` is sufficient to scope access per company.
- **Seed script demo password**: fixed string `RoughCut-Demo-1!` for the three seeded company users (admin/foreman/installer), printed to the console and documented in README.md. Not a secret — it's demo/test data only, never used for the platform owner (which comes from `.env`).
- **Seed script runner**: `supabase/seed/seed.ts` uses `@supabase/supabase-js`'s admin client (needed because creating `auth.users` rows requires GoTrue's admin API, not a plain SQL insert) and is idempotent — re-running it looks up existing users by email instead of failing.

## Shared types

- **Hand-written DB types instead of generated ones**: `packages/shared/src/types.ts` and `enums.ts` are written by hand to mirror the SQL migrations exactly, rather than running `supabase gen types typescript`, because that command needs a live, linked Supabase project (a database to introspect), which doesn't exist until deploy time. Once a real project exists, regenerating and diffing against this file is the recommended follow-up — noted again here so it isn't lost.

## Web auth + Stripe Checkout

- **Transactional email**: not wired up (no provider specified in the stack). Signup uses `email_confirm: true` on `auth.admin.createUser` so the admin can log in immediately without clicking a confirmation link. Invite emails (task: web company app) will need a real provider decision when built — flagged here so it isn't forgotten.
- **Signup error handling**: the `signup` server action never returns a value to the client; every failure path calls `redirect("/signup?error=...")` instead. This is the simplest way to surface errors from a Next.js 15 Server Action to a plain `<form action={...}>` without pulling in React 19's `useActionState` (this project pins React 18.3 to match Expo/React Native's current supported version).
- **Company row lifecycle on signup**: created *before* the Stripe customer/Checkout session, with `subscription_status: 'incomplete'` for paid plans. If Checkout is abandoned, the row stays `incomplete` (readable, but blocked from writes per the `WRITE_BLOCKING_STATUSES` list) rather than being deleted — consistent with "do not delete data." Only the auth-user and profile-insert failure paths roll back the company row, since those happen before any customer-facing redirect.
- **Stripe customer creation timing**: a Stripe customer is created during signup itself (not deferred to the webhook) so `checkout.sessions.create` can attach `company_id` in `metadata` on both the session and the subscription — the webhook handler (task 8) reads that metadata to know which company a given Stripe event belongs to, since Stripe has no native concept of "company."

## Boxes with no spec yet (sticker orders)

- **`boxes` spec columns are nullable**: the spec says the sticker order flow "creates boxes and codes immediately, then print" — meaning a box (and its code) can exist before anyone has walked the site and filled in a spec. `box_type`/`size`/`height_aff`/`circuit` are therefore nullable, with a check constraint requiring them once `status` moves past `'open'`. `'open'` now means specifically "sticker exists, nothing specified yet"; a foreman scanning such a code sees an (empty) spec form to fill in, not the read-only spec card — that distinction will matter when the mobile scan screen (task 11) is built, and is noted again there.

## Team invites

- **Invite flow creates the account immediately**: the spec says "Invite creates the user and emails a set-password link," which requires an auth user to exist before any email is sent. With no email provider configured, `createInvite` creates the `auth.users` row and `profiles` row right away (random password the invitee never sees), marks the `invites` row `accepted_at` at creation time, and generates a Supabase recovery-link (`admin.auth.admin.generateLink({type:'recovery'})`) that the company_admin copies and sends manually. The `invites` table and its 7-day `expires_at` are kept for the audit trail even though nothing currently reads `expires_at` to block an unaccepted invite, since none exist under this flow. Revisit if/when a real email provider (e.g. Resend via Supabase SMTP) is wired up — at that point `invites.accepted_at` should go back to being set only when the invitee actually sets their password.

## Super admin

- **"Suspend" semantics**: spec says "Suspend sets profiles.disabled_at and rejects writes" without saying whose. Implemented as suspending the whole company: every profile belonging to that company gets `disabled_at` set, which blocks their writes via the existing RLS/trigger checks and the login-disabled check already built for `/app`. Unsuspending clears `disabled_at` on all of them. No separate `companies.suspended` flag was added — redundant with "every profile disabled."
- **MRR calculation**: computed on read from each Stripe subscription's line items (`unit_amount × quantity`, normalized to a monthly figure by `recurring.interval`/`interval_count`), never cached or stored, per "Super admin revenue reads Stripe. Do not store a second ledger." Fine for MVP company counts; flagged in `admin-billing.ts` as the place to add caching if the admin company list grows.
- **Route structure for the owner console**: `/admin/login` sits outside the authenticated layout (a `(dashboard)` route group wraps only `/admin/companies*`), so the login page itself isn't gated by the same `requirePlatformOwner()` check it's trying to satisfy — avoids a redirect loop.

## Stripe webhook

- **Always return 200**: once signature verification passes, handler-logic errors (a DB hiccup, an unresolvable company) are logged and swallowed rather than returned as a non-2xx, since a non-2xx makes Stripe retry and the most likely failures here are application bugs a retry won't fix, not transient ones. Signature failures still return 400, which is the one case a retry (from a misconfigured endpoint) could matter.
- **Plan changes via the Customer Portal**: the spec allows the portal for "plan change and cancel," which means `customer.subscription.updated` can arrive with a different price than the company originally signed up for. The handler maps `subscription.items[0].price.id` back to `crew`/`company` by comparing against `STRIPE_PRICE_CREW`/`STRIPE_PRICE_COMPANY` and updates `companies.plan` accordingly, so a portal-initiated upgrade/downgrade is reflected without a separate code path.
- **Company resolution order**: every event handler tries `metadata.company_id` first (set at Checkout/subscription creation, see signup decisions above) and falls back to looking up by `stripe_customer_id` — covers `invoice.payment_failed`, whose invoice object doesn't carry the company metadata directly.

## Print: label art, PDF fallback, Diginate

- **Rendering stack**: `qrcode` generates the QR itself (pure JS, no native deps); the composed 2x5in label (QR + short code + "RoughCUT" wordmark) is built as an SVG string and rasterized to a 300 DPI PNG with `@resvg/resvg-js` (a prebuilt Rust binary, no system `libvips`/`cairo` dependency to worry about on a serverless host). The PDF fallback path uses `pdfkit` instead and draws text with its built-in Helvetica — deliberately NOT reusing the resvg/SVG path, so the "always works, no key needed" fallback has the fewest possible dependencies.
- **Bundled fonts, not system fonts**: `apps/web/src/lib/print/fonts/DejaVuSans*.ttf` are checked into the repo and passed to resvg via `fontFiles` with `loadSystemFonts: false`, because a serverless function's base image is not guaranteed to have any fonts installed, and silently rendering blank/boxes for label text would be a bad failure mode for physical stickers. `next.config.mjs`'s `outputFileTracingIncludes` explicitly lists these fonts so Vercel's dependency tracing (which can't see a runtime `path.join()`) still bundles them.
- **Diginate API contract is a best guess**: the build spec describes *what* must happen ("submit each as a unique image on one Diginate order, save diginate_order_id, poll status, save tracking") but not Diginate's actual endpoints/payloads, which aren't available to look up in this environment. `lib/print/diginate.ts` implements a plausible REST client (`POST /v1/orders`, `GET /v1/orders/:id`) behind the same interface the rest of the app uses, so swapping in the real contract later is a one-file change. Flagged clearly in that file's header comment — **do not treat this as verified against real Diginate docs before a live shipment.**
- **Idempotency**: boxes and their `public_code`/`short_code` are minted once, at order-submit time (see the stickers-order decision above), not inside the print pipeline — so retrying/reprinting `processStickerOrder` never mints new codes. Within the pipeline itself, `print_assets` has a unique constraint on `box_id` and every write is an `upsert`, so re-running for the same order overwrites that order's own art instead of accumulating duplicate rows. The Diginate order itself is only created once per `sticker_orders.id` (`if (!order.diginate_order_id)`); a reprint after that just re-polls status.
- **PDF fallback storage**: added `sticker_orders.pdf_path` (not in the original spec's data model) since the spec requires "a download in admin and company app" for the PDF-fallback case, and there was nowhere to put that path otherwise. `print_assets.png_path` is reused (pointing at the same shared PDF, duplicated per box) in the fallback case too, so any lookup-by-box-id code path still resolves to *something* downloadable, even though the column name is now a slight misnomer in that case.
- **Storage access**: added a `print-assets` private bucket (migration `0007`) with the same per-company-folder RLS pattern as `box-photos`. Downloads are served via short-lived (10 minute) signed URLs generated server-side with the service-role client, rather than making the bucket public.

## Mobile scaffold

- **Dynamic `app.config.ts` instead of static `app.json`**: the universal-link domain (`associatedDomains` / Android `intentFilters`) needs to match the real deployed web origin, which isn't known at template-authoring time. Reading it from a `WEB_ORIGIN_HOST` build-time env var (falling back to a `roughcut.app` placeholder) means EAS Build can inject the real domain without editing committed config — but it also means someone must actually set `WEB_ORIGIN_HOST` in EAS and publish the real `apple-app-site-association` / `assetlinks.json` files from the web app before universal links will work; this is flagged again in the mobile README section (task: README/seed/final typecheck).
- **Bundle identifiers**: `com.roughcut.app` for both iOS and Android, as placeholders — these must be real, registered identifiers before an EAS build can submit to either store. Simplest unambiguous choice given the product name; not meant to imply the real App Store Connect / Play Console app has been created.
- **Session storage**: `expo-secure-store` directly (per spec) with no chunking wrapper, since a Supabase session (short JWT + refresh token) is well under SecureStore's per-item size limit on both platforms.
- **Profile fetched client-side after session load**: `lib/auth.tsx`'s `AuthProvider` loads the Supabase session first, then separately queries `profiles` for the signed-in user — kept as two steps (rather than one joined call) so the loading flag reflects session state immediately and the profile/role (used to decide installer-vs-foreman UI) can arrive a beat later without blocking the redirect decision in `app/index.tsx`.

## Mobile screens

- **Data layer seam for the offline queue**: `lib/data/jobs.ts` and `lib/data/boxes.ts` call Supabase directly for now. They're deliberately the only places screens talk to data, so the offline sqlite queue task can swap their internals (cache-first read, queued write) without the screens changing. `lib/offline/queue.ts` is a placeholder (always-empty queue) so the Sync status screen renders correctly today and gets wired to real data next.
- **`box/[boxId]` with `boxId: "new"`**: rather than a separate route for "unknown code, foreman creates a box," the existing box-detail route special-cases the literal segment `"new"` (never a real UUID) and reads the scanned `code` from a query param. Keeps one screen responsible for "show/edit a box's spec" regardless of whether the box already exists, matching how the spec describes scan behavior as one decision tree rather than two screens.
- **Role gating on `status: 'open'` boxes**: a box minted by a sticker order has no spec yet (see earlier decision). An installer who somehow lands on one (e.g. a stale deep link) sees a plain "ask your foreman" message rather than the spec form, since installers must never get the form per spec; a foreman/admin sees the same form used for ad hoc creation.
- **Photo pipeline**: `expo-image-manipulator` resizes to the spec's 1600px long edge and re-encodes as JPEG at 0.8 quality before upload — comfortably under the 2MB cap at that resolution, so no explicit byte-size check/retry was added. Upload reads the local file via `fetch(uri).blob()` (works under Expo/Hermes with the RN URL polyfill already pulled in for Supabase) rather than a manual base64 round-trip.
- **QR scanning accepts both forms**: `extractPublicCode` parses the full `{WEB_ORIGIN}/b/{code}` URL (the actual QR payload per spec) but also accepts a bare 12-character code, in case a sticker is ever read by a generic third-party QR scanner that hands the app a different string shape via a share sheet.

## Offline sqlite queue + sync

- **Ad hoc box creation requires connectivity**: the offline queue handles "specify an existing box" and "mark installed" — both operate on a box that already has a stable server-assigned id (minted by a sticker order, or created while online), so there's nothing to reconcile once the write syncs. Creating a brand-new box from an unrecognized sticker while offline would need a temporary local id later reconciled against the server-assigned one once `boxes_before_insert` mints the real `public_code`/`short_code` — a meaningfully bigger feature the spec doesn't call out explicitly ("Offline: jobs and boxes cache in sqlite" talks about caching and the write queue in the context of specs). Given that every box a crew scans in practice was already pre-minted by a sticker order (the normal path), this gap only affects the rarer ad hoc case, so `createAdHocBoxAndSpec` simply throws a friendly "needs a connection" error offline rather than queuing. Revisit if ad hoc offline creation turns out to matter in practice.
- **Last-write-wins, implemented as "no concurrency check at all"**: queued spec writes are plain `UPDATE ... WHERE id = boxId` statements with no version/timestamp guard. Two queued writes for the same box simply apply in the order they reach the server, and whichever lands last wins — which is exactly "latest spec write wins by updated_at" (the column is stamped server-side by the existing `boxes_before_insert`/update path) without needing extra client-side conflict-detection logic.
- **Installed-never-reverts is enforced in three places on purpose**: the optimistic local cache patch (`applyLocalBoxPatch`) just sets what was asked; the real backstop is the `enforce_box_update_rules` DB trigger (migration `0003`), which has always rejected any write that would move a box off `'installed'`. The queue doesn't add its own extra check for this — it would be redundant with, and could drift from, the DB's enforcement.
- **Photo upload ordering**: a spec write with a local photo URI queues the photo as a *separate* `upload_photo` entry, created only after its corresponding `specify_box` entry successfully applies — matching "Photos upload after the row syncs" literally, and meaning a photo never gets attached to a box the server doesn't know about yet.
- **Sync triggers**: `initOfflineSync()` (called once from the root layout) processes the queue immediately on load, on every `NetInfo` reconnect event, and on every `AppState` transition to `active` (foreground) — the two triggers the spec names ("Sync on reconnect and on app foreground").
- **Queue persistence and cleanup**: the queue lives in its own sqlite table (`write_queue`), not reused from `cached_boxes`, so a queued write's lifecycle (pending → retrying → synced/failed) is independent of whatever the cache currently shows. Synced rows are kept for an hour (so the Sync status screen can show "resolved" items briefly) then deleted, rather than deleted immediately or kept forever.

## Final typecheck pass

- **`baseUrl` must be re-declared in each workspace's `tsconfig.json`, not just inherited**: the root `tsconfig.json` sets `baseUrl: "."`, but TypeScript resolves a relative `baseUrl` inherited via `extends` relative to the *defining* file's directory, not the extending one — so `apps/web/tsconfig.json` was silently resolving `@/*` against the repo root instead of `apps/web/`, breaking every `@/lib/...` import. Fixed by setting `baseUrl: "."` again explicitly in `apps/web/tsconfig.json` (it's declared directly there, so now resolves relative to `apps/web/` as intended). `apps/mobile/tsconfig.json` extends `expo/tsconfig.base` instead, which doesn't have this problem.
- **Next.js pinned to `15.5.27`**: the originally-scaffolded `15.0.3` carries a known CVE (fixed in Next's own advisory); bumped to the latest 15.x patch release rather than jumping to Next 16, to stay on the spec's named major version.
- **Stripe SDK API version string**: bumped from a guessed `2024-10-28.acacia` to `2025-02-24.acacia`, the version the installed `stripe@17.7.0` package's types actually expect.
- With these fixes, `npm run typecheck` passes across all three workspaces — the spec's explicit acceptance criterion ("npm run typecheck passes").

## iOS build/TestFlight — issues hit and fixed

- **`apps/mobile/package.json` had React Native 0.76.3 / React 18.3.1 pinned while declaring Expo SDK 54**, which actually requires React Native 0.81.5 / React 19.1.0. This was the root cause of the first build failure (CocoaPods couldn't find `ReactAppDependencyProvider`, a pod that only exists in RN 0.81+'s architecture). Fixed by aligning every `expo-*` package and `react`/`react-native` to the versions in Expo's official SDK 54 `bundledNativeModules.json`. Verified with `npx expo-doctor` (18/18 checks passing) and a full `npm run typecheck` (zero errors, no code changes needed) before rebuilding.
- **Metro couldn't resolve the app entry point** (`Unable to resolve module ../../App from .../expo/AppEntry.js`) despite `"main": "expo-router/entry"` being set correctly in `package.json` — a known quirk of `expo export:embed --eager` (the command EAS Build uses) in nested-workspace monorepos, where it doesn't always honor the `main` field. Fixed by adding an explicit `apps/mobile/index.js` containing `import "expo-router/entry";`, which Metro resolves directly regardless of the `main` field quirk.
- **EAS project ID**: since `app.config.ts` is a dynamic (TypeScript) config, `eas build` cannot auto-write the EAS project ID into it the way it can for a static `app.json`. Added `extra.eas.projectId` manually after `eas project:init` generated it (`536eaa8f-392c-4274-9952-9a6d33986311`, under the `@nrealm/roughcut` Expo account).
- **`ITSAppUsesNonExemptEncryption: false`** added to `ios.infoPlist` — RoughCUT only uses standard HTTPS/TLS, no custom encryption, so this answers Apple's App Store Connect export-compliance question automatically instead of prompting on every submission.
- iOS distribution certificate and provisioning profile were generated and are stored remotely by EAS (not in this repo) — reusable for all future builds without re-prompting.
